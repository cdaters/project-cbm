## A. Executive Summary

**The published Project CBM v1.0.0 image is already Raspberry Pi OS Lite 64-bit / Debian 13 Trixie. It is not Bookworm.** This is established by inspecting the SHA-256-verified release image, not by interpreting its documentation. The owner confirmed during this audit that there is no separate Bookworm image to recover and that the remembered OS generation was mistaken.

The correct next-generation objective is therefore **a current-Trixie refresh and reproducible integration/build system**, with reliability and release cleanliness improvements. Calling 1.1 “Trixie Edition” remains possible, but release notes must not describe it as the first Trixie generation.

The current runtime architecture is appropriate in broad outline: console appliance, Bash/dialog menu, SDL2 VICE, direct ALSA audio, ordinary Linux services, and simple user-owned content directories. There is no evidence justifying a menu rewrite, desktop, web server, containerized runtime, or broader emulation distribution.

The most important findings are:

1. Both local checkouts are clean but **26 commits behind their actual GitHub main branches**. Their local `origin/main` refs are stale, so local status alone gives a misleading impression of being current.
2. The public image and the formal Menu v1.0.0 release are related but **not identical**. Of 17 shipped scripts, 12 match the Menu tag and five differ; the tag adds an eighteenth, experimental screenshot helper. No available Menu commit exactly matches the shipped runtime.
3. The image includes reusable machine identity, SSH host keys, processed cloud-init state, shell history, build trees, and content that contradicts blanket “no ROMs/disk images” statements. Image sealing and content provenance are release priorities.
4. The sudo policy permits unrestricted root `tee`, `mount`, `rm`, and `mkdir`. It is not a narrow privilege boundary. The published image also enables TCPser despite the documented disabled default.
5. Existing tooling packages source ZIPs, not complete images. CI still builds a `6.5` bundle and watches `menu-v*` tags while the formal version is `1.0.0` with a `v1.0.0` tag.
6. Preserve 1.0 accurately as the original Trixie generation; create a maintenance line only after recording the image/source differences. Develop 1.1 from current remote source with explicit release inputs and Pi 3 qualification gates.

**Recommendation:** keep the repositories separate; make `project-cbm` own image integration, build inputs, qualification, release artifacts, and public documentation. Keep `project-cbm-menu` responsible for its independently versioned menu, launcher interface, assets, and focused tests. Prefer a pinned pi-gen arm64 Lite build plus a small Project CBM stage for 1.1, with versioned packages for custom software. See F for alternatives and the conditions for revisiting that recommendation.

### Runtime flow and capabilities

```text
Pi firmware -> model-appropriate kernel/initramfs -> multi-user.target
  -> getty tty1 autologin as pi -> ~/.profile -> pcbm-start
      -> menu, or saved default machine -> menu after VICE exits
  -> menu/helpers -> SDL2 VICE -> ALSA audio -> return to console
```

The normal default is `menu`, with `x64sc` as the saved machine and F10 as VICE's menu key. Machine profiles include `x64`, `x64sc`, `xscpu64`, `x64dtv`, `x128` in 40/80-column modes, `xcbm2`, `xcbm5x0`, `xvic`, `xplus4`, and `xpet`. VICE tools `c1541`, `cartconv`, `petcat`, and `vsid` are installed, although `vsid` is not a dedicated menu workflow.

The menu recursively scans content and uses the currently selected machine for `-autostart`; it does not reliably distinguish disks, tapes, cartridges, SID music, expansion images, or ROM configuration. USB import selects the first removable partition, copies into content categories, and normally skips existing files. ROM import is a separate copy workflow. Midnight Commander provides manual file management.

The image contains a guest-disabled writable Samba share named `Project CBM`, restricted to `pi`, with SMB on TCP 445 and NetBIOS disabled. However, the older network helper still starts/stops `nmbd`, and enabled-unit links also include `nmbd`, `winbind`, and `samba-ad-dc`. Enabled links do not prove those services successfully run. SSH and Samba enabled-at-boot configuration agrees with the documented policy; TCPser's enabled link contradicts its documented disabled default.

TCPser's unit uses `-s 2400 -l 7 -p 0 -v 6400`, user/group `pi`, and `network-online.target`. Treat this as an unqualified integration: service existence is not proof of a working VICE IP232/modem session. Neither installed VICE configuration nor this audit demonstrates a completed BBS connection.

The documentary hardware target is Pi 3, Pi 4/400, Pi 5/500. No repeatable benchmark records establish qualification on all of them. The dated build diary explicitly says development was focused on Pi 5/500. No actual Pi was booted during this audit.

### Suitability and concrete defects

Keep Bash/dialog. It is small, understandable, already separated into helpers, and supported in Trixie. There is no obsolete GUI framework to replace. The real maintenance work is tightening interfaces and error handling.

Priorities established by source inspection:

- The root sudo grants allow arbitrary arguments to general-purpose file-writing and mounting commands. Replace them with narrowly validated operations; keep ordinary preferences user-writable.
- The installer resets boot/default-machine configuration, cannot target an alternate root filesystem, and installs sudoers before validating it. It is a source-Pi installer, not an idempotent image/update installer.
- The docs-sync script's `--dry-run` still uses `cp -n` and `mkdir`, which can create missing files/directories. `--apply` uses `rsync --delete` on public docs directories and can erase public-only pages. Do not run it during recovery.
- Machine and content launch paths differ in binary resolution, validation, splash handling, and custom ROM handling. Route them through one tested launcher contract.
- USB detection checks `RM`, not whether the partition is suitable USB content storage; it neither selects among disks nor excludes the root/boot storage robustly. The default mount is writable with no explicit `nodev,nosuid,noexec` policy. Cleanup does not guarantee unmount on every signal/error.
- NUL-safe discovery becomes newline-delimited selected paths; unusual filenames can break import. Existing-file skips are counted as successful items, and partial errors need clearer reporting.
- Every recursive content result becomes a command argument to dialog; sufficiently large collections can hit argument-size or responsiveness limits. Directory browsing or bounded lists are enough; a database is not required.
- `pcbm_service_active` can misclassify missing units and duplicate “inactive”; BBS status treats a stopped service as missing. Network tests conflate DNS resolution with successful ICMP replies.
- `.asoundrc` and audio state are rewritten at launch; manual output settings store numeric card indices. Use stable device identity and atomic writes, while retaining the simple ALSA design.
- Version fields are already broken in the formal tag. CI success currently verifies ZIP packaging, not menu behavior or image correctness.

## E. Technology Modernization Audit

Classifications describe the proposed 1.1 direction. Hardware-dependent conclusions remain qualification gates, not claims of measured compatibility.

| Component or method | Decision | Reason and proposed treatment |
| --- | --- | --- |
| Raspberry Pi OS Lite | KEEP | Matches appliance goals and supplies supported Pi kernel/firmware integration |
| Dated OS/packages | UPDATE | Refresh the already-Trixie base, explicitly recording release date, package inputs, kernel and firmware |
| arm64 runtime | KEEP | Already used; one image serves the requested CPU generations. Qualify 512 MiB Pi 3A+ as well as 1 GiB Pi 3B |
| Vendor kernels/firmware | UPDATE | Preserve both v8 and 2712 kernels/initramfs and appropriate firmware/DTBs; no custom kernel or `rpi-update` dependency |
| VICE 3.10 SDL2 UI | KEEP | Current official release; console UI suits the product despite upstream's general GTK3 preference |
| Manual VICE `make install` | REPLACE | Build a pinned source release in a clean build environment; produce a versioned package and build log |
| Distro SDL2/Mesa | KEEP | Already current Trixie SDL2 ABI; use distribution packages and test backend behavior. Do not introduce a private SDL build without a demonstrated defect |

### Current upstream facts supporting the decisions

- Raspberry Pi's current download page lists **2026-06-18 Lite 64-bit, Debian 13 Trixie, kernel 6.18**, and explicitly includes Pi 3A+/3B/3B+, 4/400, 5/500/500+ compatibility. This is a candidate input, not a Project CBM qualification result. The page lists SHA-256 `acff736ca7945e3b305f07cda4abdb870910e12634991da69783611756e381b3`; it was not downloaded in this audit. [Official OS downloads](https://www.raspberrypi.com/software/operating-systems/).
- VICE's official release page still lists **3.10**, released December 24, 2025. Its 3.10.1 page is a development work list, including joystick/keyset persistence issues, not sufficient evidence of a published release. Keep 3.10 as the first comparison baseline and re-evaluate a real subsequent release at input freeze. [VICE releases](https://vice-emu.sourceforge.io/), [upstream 3.10.1 work list](https://vice-emu.pokefinder.org/wiki/3.10.1).
- Debian Trixie's `vice` package is **3.9+dfsg-1**, GTK-oriented and without the ROM images required to run emulators. It is not a drop-in replacement for this 3.10 SDL2 appliance. Trixie supplies SDL2 **2.32.4+dfsg-1** and dialog **1.3-20250116-1**, both already present in the public image. [VICE package](https://packages.debian.org/trixie/vice), [SDL2 package](https://packages.debian.org/trixie/libsdl2-2.0-0), [dialog package](https://packages.debian.org/trixie/dialog).
- Raspberry Pi OS uses cloud-init and Netplan, with NetworkManager as its default renderer. Do not add a competing first-boot network rewrite. Current Imager supports explicit customization formats; a locally selected custom image defaults to no customization metadata, so “Use custom” must be tested separately from a custom OS manifest. [Raspberry Pi cloud-init guidance](https://www.raspberrypi.com/news/cloud-init-on-raspberry-pi-os/), [Imager customization contract](https://github.com/raspberrypi/rpi-imager/blob/main/doc/os_customisation_formats.md).
- Raspberry Pi OS changed new-install sudo defaults in April 2026. The appliance should provide explicit limited permissions rather than depend on blanket passwordless sudo. [Official security update](https://www.raspberrypi.com/news/a-security-update-for-raspberry-pi-os/).
- Pi 5/500/500+ normally use the 2712 kernel, including its different page-size assumptions; older arm64 models use the v8 kernel. Preserve vendor selection and matching initramfs. SDL2 offers a KMS device-index hint, but numbering must not be treated as a permanent hardware identity. [Kernel selection](https://www.raspberrypi.com/documentation/computers/config_txt.html#kernel), [SDL KMS hint](https://wiki.libsdl.org/SDL2/SDL_HINT_KMSDRM_DEVICE_INDEX).
- TCPser's latest tagged release is **1.1.4 (2020)**, while the recovered source commit identifies **1.1.6_beta (2023)**. Pinning the actual lineage is more meaningful than selecting a tag solely because it is called stable. [TCPser releases](https://github.com/go4retro/tcpser/releases), [recovered upstream commit](https://github.com/go4retro/tcpser/commit/fe7feff4862406b277e009d14c219f5d16cf1222).
- Samba's Unix-password synchronization setting synchronizes Unix credentials when Samba credentials change; it does not establish that changing the Linux password via raspi-config updates Samba's credential database. Correct the existing user advice and test both flows. [Samba configuration reference](https://www.samba.org/samba/docs/current/man-html/smb.conf.5.html).

## F. Reproducible-Build Options and Recommendation

### What exists

The current process is flash stock OS, update interactively, install packages, build VICE and TCPser on a Pi, copy menu/configuration, manually validate, clean the running Pi, capture its card, shrink, compress and upload. The Menu Makefile/CI builds ZIPs only. There is no end-to-end image recipe, package lock, complete manifest, or demonstrated reproducible build.

### Options

| Option | Advantages | Costs / limitations | Decision |
| --- | --- | --- | --- |
| Scripted customization of a checksum-pinned official Lite image | Literal release-X input; smallest distance from official image; preserves vendor defaults | Must safely manage image resizing, mounting/chroot, cleanup and sealing; added APT inputs still need retention | Good fallback or prototype, but avoid building a large home-grown image framework |
| Pinned pi-gen arm64 stages 0-2 plus Project CBM stage | Upstream Raspberry Pi OS builder; existing shell ecosystem; Lite baseline; partition/export/expansion tooling | More build work than patching an image; APT archives must still be frozen; builder config does not recreate an official XZ byte for byte automatically | **Preferred initial 1.1 architecture** |
| Pinned rpi-image-gen | Purpose-built custom appliance assembly, layers, manifests/SBOM support; potentially leaner rootfs | Additional layer/config knowledge; rapid upstream change; host and universal-device profile need validation; not automatically the same product as Raspberry Pi OS Lite | Strong alternative if the pi-gen prototype shows concrete limitations |
| New custom debootstrap/mmdebstrap builder | Maximum control | Project owns boot/firmware/image assembly details already handled upstream | Do not choose for 1.1 |
| Keep hand-built card plus more instructions | Low immediate effort | Retains drift, secrets, unknown dependencies and manual state | Historical recovery only |

pi-gen documents separate arm64 and 32-bit branches, staged builds, and XZ export. Use a recorded commit, not a moving branch. rpi-image-gen's current release is **v2.8.0**, August 13, 2026; it has active configuration changes and explicit host requirements. Neither tool's name guarantees deterministic output. [pi-gen arm64](https://github.com/RPi-Distro/pi-gen/tree/arm64), [rpi-image-gen](https://github.com/raspberrypi/rpi-image-gen), [v2.8.0 release](https://github.com/raspberrypi/rpi-image-gen/releases/tag/v2.8.0).

Use a native arm64 Debian/Raspberry Pi OS build host initially, with enough RAM/storage to build comfortably. A Pi 4/5 build machine does not raise the runtime minimum. The Mac can orchestrate; native macOS is not the intended Linux image-building environment. Keep cross-architecture QEMU/CI as a later convenience unless already available and proven. Do not run privileged image jobs for untrusted pull requests on a persistent release host.

### Proposed pipeline

```text
Product release lock
  -> verify/download retained inputs
  -> clean target-architecture package builds
  -> pi-gen Lite stages + CBM integration
  -> offline image checks and sealing
  -> physical-Pi qualification
  -> final image, compressed image, checksums, manifest, notes
```

`project-cbm` should own a compact machine-readable release lock (JSON is sufficient) containing:

- Product version, edition/base release date, target architecture and supported hardware policy.
- Builder repository commit, configuration hash, host/toolchain versions and build environment identity.
- Official base image URL/hash if used, or the exact pi-gen base recipe and package source state if constructing Lite from packages. Label these accurately; they are different inputs.
- Debian and Raspberry Pi APT origins, authenticated index metadata, exact package versions and hashes, including transitive dependencies.
- VICE source URL, checksum, patches, configure/compiler flags, package version, source package and resulting package hashes.
- TCPser source commit and package identity.
- Menu semantic version, tag name, peeled commit, package/bundle hash, configuration schema compatibility.
- Integration commit, configuration/assets hashes, allowed starter-content inventory and provenance.

For custom software, prefer simple Debian packages built once and installed into the image. Separate `pcbm-menu` from product integration and VICE/TCPser packages. This supplies ownership, dependencies and upgrade behavior without a private network package server at the outset. Packages can be installed from a retained local build repository. Do not install into `/usr/local` using a package without deliberately resolving Debian filesystem conventions; adjust the launcher contract to the chosen packaged path.

**Package version strings alone are insufficient.** An upstream repository may remove a package. Retain the full downloaded `.deb` closure and signed index metadata, or use a verified snapshot service where available. Do not assume Debian snapshots also retain Raspberry Pi's repository. A plain caching proxy is not a permanent archive. Separate networked input acquisition from a build that can be repeated using the retained inputs.

Output should include `.img`, `.img.xz`, `SHA256SUMS`, machine-readable build/release manifest, package inventory/SBOM, source/build logs, release notes, qualification results and a public documentation bundle. Record the compressed and uncompressed hashes. Pin source-fetch and CI actions by commit; fail on dirty source, missing inputs, mismatched versions and checksum errors.

### Reproducibility definition

For 1.1, require clean repeatable builds with identical input manifests, package sets, application files and configuration. Build twice in clean environments and compare artifacts. Normalize ordering, timestamps, archive metadata, build paths, locale/timezone and filesystem identifiers where practical. Inspect any remaining difference rather than claiming bit-for-bit reproducibility prematurely.

Runtime identities must be generated per device on first boot, not made deterministic inside the distributed image. Keep those distinctions explicit in the manifest. A deterministic image and unique SSH keys are compatible goals.

Image creation should eliminate live-card sanitation as the normal workflow. One tested first-boot mechanism should expand storage, initialize identity/account state and record successful completion. Do not layer PiShrink's `rc.local` expansion over cloud-init growth and another custom resize service.

## G. Preservation Recommendation

### Corrected OS history

There is no verified Bookworm generation to preserve. The owner confirmed the downloaded public image is the intended v1.0 baseline. Do not create a `bookworm` branch from Trixie source or relabel v1.0 history. The useful policy is:

```text
Project CBM 1.0.x: original Trixie appliance generation; important fixes only
Project CBM 1.1.x: current Trixie, reproducible builds and active modernization
```

### Permanent preservation, after approval

1. Archive exact public image, both distinct released docs ZIPs, Menu bundle, checksums, release JSON and all referenced Git objects outside GitHub in durable storage. Maintain at least two independent copies and periodically verify hashes.
2. Archive original and current remote Git histories with all refs. Include annotated tag objects, the skeleton backup ref, and draft release metadata. Temporary audit clones are not the permanent archive.
3. Store the extracted as-shipped scripts/configuration and a file-hash manifest as a clearly labeled recovery snapshot. Preserve its original version metadata. Add a provenance note explaining the five script differences and missing screenshot helper.
4. Keep existing `v1.0.0` tags and attached assets unchanged. Add correction/provenance documentation in new commits. Any decision to change public availability because of identity/content findings should preserve the original privately first and should be reviewed separately.
5. For product maintenance, create `maintenance/1.0` from the product release tag, then deliberately bring forward relevant public documentation corrections. For Menu, create a recovery commit representing the actual shipped runtime before using it as a maintenance baseline; retain the existing formal Menu tag as a separate artifact. Alternatively base maintenance on the formal tag only with an explicit release reconciliation changelog.
6. Use a unique recovery name such as `recovered/image-v1.0.0-runtime`, never repoint Menu `v1.0.0`. Record the recovered commit in the product manifest once authorized.
7. Protect release tags and maintenance branches. New immutable/signed releases can strengthen future preservation; do not rewrite existing tags to add signatures.

A 1.0.1 maintenance release is worth considering for identity/credentials, truthful release metadata and major integration defects. It must have a new image, checksums, provenance and qualification. Do not silently replace the original 1.0.0 image, and do not create a new Bookworm target merely to fit the original version plan.

## H. Trixie Development Recommendation

After preservation and direction approval, fast-forward both original clean local `main` branches to verified remotes. No forced reset is necessary. Then use short feature branches off `main` for 1.1, reserving `maintenance/1.0` for selected fixes. A separate long-lived `develop` branch is not needed for this project size.

The first development milestone should reproduce the current feature set from declared inputs. Start with VICE 3.10 and the known SDL2/ALSA architecture to isolate image/build changes. Move to the selected current Raspberry Pi OS base deliberately, recording kernel/Mesa/firmware deltas and testing Pi 3 early.

Version the Menu independently. A product candidate must consume a specific Menu candidate/release tag plus commit and hash; a menu change need not force the same numerical product version. Use `v1.1.0-rc.N` conventions in the respective repositories and enforce that the embedded manifest agrees with the build inputs. Shared numerical versions must never substitute for dependency mapping.

No in-place distribution conversion is needed: 1.0 is Trixie already. Still prefer backup, fresh 1.1 flash, and validated restore because permissions, configuration ownership, service policy and image identity will change. Document ordinary security-update policy separately from release upgrades. Do not freeze vulnerable packages forever merely to preserve a historic build: preserve release inputs while publishing tested maintenance updates.

## K. Risks and Unresolved Questions

### Release risks established by this audit

1. **Image identity and residual state:** all three standard SSH private host-key files exist, `/etc/machine-id` is nonempty, cloud-init has processed the same instance ID present on the boot partition, and the instance has a completed SSH semaphore. This strongly suggests cloned identity can persist; confirm on two fresh cards. No private key contents were displayed or exported into this report. Shell history is nonempty (8094 bytes), and build/source trees remain.
2. **Excessive privilege:** root `tee` with arbitrary paths can overwrite privileged configuration. Combining public credentials, SSH and such permissions is a concrete exposure. The audit did not attempt an exploit or authenticate using the documented default password.
3. **Content/provenance contradiction:** the image contains VICE C64 ROM files, demos, disk images, magazine scans, and a file named `impossible_mission.d64`. Filenames do not establish redistribution rights; neither “freeware” nor a general disclaimer is a provenance record. Reconcile actual content with permissions before another public image. VICE itself is GPL-licensed; preserve corresponding source and license information. [VICE licensing](https://vice-emu.sourceforge.io/).
4. **Source-release mismatch:** consuming Menu v1.0.0 is a code change relative to the image, including fixes and newly broken version text. It cannot be substituted silently when reconstructing 1.0.
5. **Misleading successful CI:** existing runs succeed at building the incorrectly named 6.5 ZIP. They do not validate image composition, version metadata or runtime functionality.
6. **Installer/docs synchronization:** reinstall resets preferences, and the purported dry run can write. The apply path can remove public-only documentation. Recovery must not use these helpers without correction.
7. **Storage assumptions:** removable-bit detection is not a safe definition of USB content media; PiShrink's fallback assumes SD on `mmcblk0`. USB-root and NVMe support need explicit tests.
8. **Incomplete service policy:** TCPser is enabled while docs say disabled; Samba service links and helper disagree with SMB-only configuration. A stopped service and an absent service are not interchangeable.

### Hardware and engineering unknowns

- Actual boot latency, idle memory and VICE speed on Pi 3B/3A+; no measurements were fabricated.
- SDL's actual video backend/renderer, DRM device ownership, fbi coexistence, display-mode selection and capture behavior across 3/4/5/500+.
- Reliable Pi 3A+ memory headroom with network services and large content lists; compilation parallelism is a separate build-host concern.
- Audio sink numbering across models, HDMI hotplug, USB devices, and exit from speaker tests.
- Keyboard/keyset persistence given known upstream mapping issues; controller enumeration and identical-controller identity.
- Whether TCPser's IP232 listener is appropriately bound and usable with the shipped VICE defaults. Inspect upstream behavior and confirm with a controlled network test before enabling remote listeners.
- EEPROM and NVMe behavior on a physical 500+; OS compatibility does not prove this particular historical image supports it.
- Exact original official-base XZ checksum and full historical input lock: embedded base date/pi-gen commit are known, but the original base artifact and every historical download were not archived as a release manifest.
- VICE source modifications beyond the retained tar/build metadata and compiler environment; installed x64sc matches retained build output, but no clean independent build was run.
- Final package archive retention mechanism, supported build host, and acceptable reproducibility level after the first double-build comparison.
- Exact content licenses and whether any residual history/provisioning files contain private data. Do a controlled review before publishing further extracts; this audit deliberately avoided printing secrets.

### What was and was not verified

Both original worktrees remained clean. All 18 remote Menu scripts and four packaging scripts passed individual Bash syntax checks; all 17 extracted image scripts passed as well. The release image/docs checksums and Menu bundle/tag correspondence were verified. These are static/integrity checks, not runtime tests. No Pi, emulator session, network service, installer, docs-sync, release-prep, or image builder was executed. No hardware access was available, and no source tarball checksum was independently confirmed after the SourceForge transfer failed.
